# Dental IS — 6 промптов для реализации через ИИ-агентов (Claude Code)

Как использовать этот файл:

- Это исходное ТЗ разбито на **6 последовательных фаз**. Каждая фаза — самостоятельный промпт, который можно целиком скопировать в новую сессию Claude Code (или другого агента).
- Фазы **строго последовательны**: 2 зависит от результата 1, 3 от 2, и т.д. Не начинайте фазу N, пока фаза N-1 не завершена и не работает end-to-end.
- В начале каждого промпта — блок "Контекст", который стоит держать прикреплённым к сессии (или вставлять заново), чтобы агент не терял общую картину архитектуры, даже работая только над своей частью.
- В конце каждого промпта — "Definition of Done": не переходите к следующей фазе, пока пункты не выполнены.
- Исходный полный текст ТЗ рекомендуется держать в репозитории как `docs/TZ.md` и явно указывать агенту читать его при необходимости деталей, не продублированных здесь.

## ЧАСТЬ 1 / 6 — Фундамент: архитектура, Domain, БД, локальный запуск

```
Ты реализуешь проект "Dental IS" — локальную стоматологическую информационную
систему для одного врача (один врач = один администратор), полностью офлайн,
без сервера и облака. Это ФАЗА 1 из 6 общего плана. Твоя задача — заложить
фундамент, на котором будут строиться все остальные фазы. Ничего из UI и API
пока не требуется — только Domain, Infrastructure и механизм локального запуска.

СТЕК:
- .NET 9, C#, Clean Architecture
- PostgreSQL (локальный, portable, embedded — без системной установки)
- EF Core (Code First + миграции)
- Serilog для логирования
- Solution из проектов: DentalSystem.Domain, DentalSystem.Application,
  DentalSystem.Infrastructure, DentalSystem.WebApi, DentalSystem.Client (Blazor WASM),
  DentalSystem.Shared

ЗАДАЧИ ЭТОЙ ФАЗЫ:

1. Создай solution и все 6 проектов с правильными ссылками между слоями:
   Domain не зависит ни от чего. Application зависит только от Domain.
   Infrastructure зависит от Application и Domain. WebApi зависит от Infrastructure,
   Application, Shared. Client зависит только от Shared. Никаких циклических зависимостей.

2. Реализуй в Domain все сущности и enum'ы по модели данных ниже (полный список —
   17 таблиц + связанные сущности из раздела 19 ТЗ). Для каждой — POCO-класс,
   без атрибутов EF Core (конфигурация через Fluent API в Infrastructure).

   Основные сущности: Patient, Visit, Procedure, VisitProcedure, Tooth,
   ToothSurfaceHistory (append-only журнал), TreatmentPlan, TreatmentPlanItem,
   Payment, Attachment, Material, MaterialUsage, Prescription, Reminder,
   AuditLog (append-only), Settings (singleton), Icd10Codes, Icd11Codes,
   Currency, DiscountHistory, WaitingList, BackupRecords.

   Обязательные доработки полей по разделу 19 исходного ТЗ:
   - Procedure: добавить Specialty (расширяемый справочник, НЕ жёсткий enum),
     PriceMin/PriceMax (вместо единой Price там, где применим диапазон),
     WarrantyMonths, RequiresConsent, DefaultDiscountPercent.
   - VisitProcedure: WarrantyMonths (снапшот на момент визита), Price (снапшот).
   - Visit: добавить отдельное поле Diagnosis (varchar/text) — НЕ смешивать
     с DoctorNotes, т.к. по разделу 19.4 это разные вещи в UI.
   - Patient: добавить Source (источник пациента: реклама/рекомендация/соцсети).

   Полные схемы полей всех таблиц — см. приложенный docs/TZ.md, раздел 4 и 19.6.
   Перенеси их в Domain-сущности без потери ни одного поля.

3. Value Objects / доменные исключения где уместно (например DebtCalculation,
   исключение при попытке физически удалить пациента с историей).

4. Реализуй Repository Pattern + Unit of Work интерфейсы в Application
   (сами интерфейсы — в Application, реализация — в Infrastructure).

5. EF Core:
   - DbContext со всеми DbSet.
   - IEntityTypeConfiguration<T> для КАЖДОЙ сущности отдельным файлом.
   - Все FK — ON DELETE RESTRICT для медицинских данных, кроме черновиков
     TreatmentPlan (Draft можно удалить).
   - Индексы: FullName (GIN trigram), Phone, CardNumber, BirthDate на Patient;
     PatientId+VisitDate на Visit; GIN на tsvector для полнотекстового поиска
     по DoctorNotes/DoctorComment (раздел 17.6).
   - SQL VIEW patient_debts (раздел 4.10) — через миграцию с raw SQL
     (HasDbFunction или Migration.Sql).
   - Первая миграция создаёт всю схему.

6. Локальный запуск PostgreSQL (portable, без системной установки):
   - Открой архитектурное решение: как встраивается portable PostgreSQL
     (бинарники в Database/pgsql/, data directory в Database/data/).
   - Напиши сервис PostgresBootstrapService (в Infrastructure), который:
     проверяет, запущен ли Postgres на нужном порту → если нет, запускает
     процесс pg_ctl из портативной поставки → если data directory пустой,
     выполняет initdb → проверяет/создаёт БД dental_system → это ДОЛЖНО
     работать через Process.Start, без Docker.
   - Учти graceful shutdown (SIGTERM/событие закрытия приложения) —
     аккуратная остановка Postgres-процесса.

7. Создай файловую структуру на диске при первом запуске (раздел 3 ТЗ):
   App/, Database/pgsql/, Database/data/, Backups/{daily,pre-update,manual}/,
   Patients/{id}/{Photos,XRays,CT,Documents,Reports}/ (создаётся динамически
   при создании пациента), Reports/, Logs/, Settings/, Temp/, Cache/, Exports/,
   Imports/. Все пути в БД — относительные от корня DentalSystem/.

8. Serilog: файлы Logs/log_YYYY-MM-DD.txt, ротация ежедневная, хранение 30 дней,
   уровни Information/Warning/Error/Fatal, плюс консоль в Debug-конфигурации.

9. Program.cs (пока минимальный, без контроллеров) должен на старте:
   проверить/запустить Postgres → проверить/создать БД → Database.Migrate() →
   создать запись Settings с PIN по умолчанию "1998" (bcrypt-хэш, НЕ plaintext),
   если её нет → создать файловую структуру → сделать стартовый pg_dump backup
   (можно вызовом Process на pg_dump.exe из портативной поставки) → залогировать
   успешный старт.

10. Напиши integration/unit тесты (xUnit) как минимум: миграции применяются
    без ошибок на чистой БД; PostgresBootstrapService идемпотентен (повторный
    запуск не ломает существующие данные); VIEW patient_debts возвращает
    корректный агрегат на тестовых данных.

DEFINITION OF DONE:
- [ ] Solution собирается без ошибок, слои не имеют циклических зависимостей
- [ ] Все сущности из раздела 4 и 19 ТЗ перенесены в Domain без потери полей
- [ ] EF Core миграция создаёт полную схему + VIEW patient_debts
- [ ] Запуск проекта (dotnet run в WebApi) автоматически поднимает portable
      Postgres, создаёт БД, применяет миграции, создаёт файловую структуру,
      создаёт Settings с PIN 1998 (bcrypt), делает стартовый backup —
      всё это видно в логах Logs/
- [ ] Повторный запуск идемпотентен (ничего не падает и не дублируется)
- [ ] Тесты зелёные
```

## ЧАСТЬ 2 / 6 — Application: CQRS, валидация, аудит, backup-сервис

```
Продолжение проекта Dental IS. ФАЗА 2 из 6. Фундамент (Domain + Infrastructure +
локальный запуск Postgres) уже реализован в фазе 1 и работает — не переделывай
его, опирайся на него. Твоя задача — построить Application-слой: CQRS через
MediatR, валидацию, маппинг, pipeline behaviors и сервис резервного копирования.

СТЕК ДОБАВЛЯЕТСЯ: MediatR, FluentValidation, AutoMapper, Result Pattern.

ЗАДАЧИ ЭТОЙ ФАЗЫ:

1. Введи Result<T> (успех/ошибка с человекочитаемым сообщением) как способ
   возврата бизнес-ошибок из всех Command/Query Handler'ов. Бизнес-ошибки
   НЕ выбрасываются как исключения (например "нельзя удалить пациента с
   активными визитами" — это Result.Failure, а не exception).

2. Реализуй MediatR pipeline behaviors:
   - ValidationBehavior — прогоняет каждую команду через FluentValidation
     Validator перед хендлером, при ошибке валидации возвращает Result
     с validationErrors, хендлер не вызывается.
   - AuditLoggingBehavior — после каждой команды, изменяющей данные,
     пишет запись в AuditLog (EntityType, EntityId, Action, ChangesJson
     со старым/новым значением, Timestamp).

3. Реализуй полный набор Command/Query + Handler + Validator + AutoMapper
   Profile для каждого модуля (см. полный список в разделе 5 исходного ТЗ):

   Patients: CreatePatientCommand, UpdatePatientCommand, ArchivePatientCommand,
   GetPatientByIdQuery, SearchPatientsQuery (пагинация + фильтры: имя, телефон,
   дата рождения, номер карты, наличие долга), GetPatientTimelineQuery.
   — SearchPatientsQuery обязан проверять похожих пациентов (похожее ФИО +
     дата рождения) и в отдельном флаге результата сигнализировать о
     возможном дубле — под UI-предупреждение "возможно такой пациент уже есть"
     (раздел 17.13).

   Visits: CreateVisitCommand, UpdateVisitCommand, CancelVisitCommand
   (мягкая отмена, Status=Cancelled, запись не удаляется), CompleteVisitCommand,
   GetVisitByIdQuery, GetPatientVisitsQuery, GetUpcomingVisitsQuery.
   — CreateVisitCommand должен принимать: процедуры (с ToothNumber/SurfaceCode
     где применимо), диагноз (отдельное поле Diagnosis), DoctorNotes, и
     атомарно (в одной транзакции) создавать Visit + VisitProcedure[] +
     ToothSurfaceHistory[] (с привязкой VisitId) + обновлять Patient.LastVisitDate
     + списывать материалы (если переданы) через MaterialUsage с проверкой на
     отрицательный остаток (предупреждение в ответе, не блокировка).
   — После процедур с непустым AutoFollowUpDays (лечение каналов, коронка,
     имплантация — настраивается в каталоге Procedure) — автоматически
     создавать Reminder на N дней вперёд (раздел 17.13, "забытый повторный визит").

   Teeth: UpdateToothStatusCommand, AddToothSurfaceRecordCommand (создаёт запись
   в ToothSurfaceHistory, append-only, никогда не редактирует существующие),
   GetPatientOdontogramQuery, GetToothHistoryQuery, GetSurfaceHistoryQuery.
   — Добавь BulkUpdateToothStatusCommand — применение одного диагноза/статуса
     к нескольким выбранным зубам одним действием (раздел 17.13, мультивыбор).

   TreatmentPlans: CreateTreatmentPlanCommand, AddTreatmentPlanItemCommand,
   CompleteTreatmentPlanItemCommand, GetTreatmentPlanQuery.

   Payments: RegisterPaymentCommand, RegisterRefundCommand (создаёт отдельную
   запись Type=Refund, НИКОГДА не редактирует/удаляет исходный платёж — раздел
   17.13), PayOffDebtCommand (частичная оплата, раздел 17.5 — Amount вводится
   вручную, может быть меньше остатка долга), GetPatientPaymentsQuery,
   GetDebtorsListQuery (с фильтрами по сумме, дате, и обязательным вычислением
   "давности долга в днях" с порогами: жёлтый 1–30 дней, красный >90 дней —
   раздел 19.2).

   Attachments: UploadAttachmentCommand (сохраняет файл в Patients/{id}/{тип}/,
   считает SHA-256, генерирует thumbnail для изображений, пишет запись в БД),
   DeleteAttachmentCommand (мягкое удаление), GetPatientAttachmentsQuery.
   — Поддержи разметку фото "До лечения"/"После лечения" (раздел 17.13) —
     добавь поле PhotoStage в Attachment (enum: None, Before, After).

   Materials: CreateMaterialCommand, UpdateStockCommand, GetLowStockMaterialsQuery,
   GetMaterialUsageReportQuery.

   Reminders: CreateReminderCommand, CompleteReminderCommand, GetActiveRemindersQuery.

   Analytics: GetDashboardStatsQuery, GetRevenueByPeriodQuery,
   GetPopularProceduresQuery, GetPatientFlowStatsQuery, GetDoctorWorkloadStatsQuery
   (тепловая карта по часам/дням, средняя длительность визита, % простоя,
   % отмен/неявок — раздел 17.8), GetInactivePatientsQuery ("отвалившиеся"
   пациенты без визита более N месяцев — раздел 17.13).
   — Добавь расчёт реальной прибыли по визиту/периоду: выручка минус
     себестоимость списанных материалов (MaterialUsage.QuantityUsed *
     PricePerUnit) — раздел 17.13.

   Backup: CreateManualBackupCommand, RestoreBackupCommand, GetBackupsListQuery,
   ValidateBackupIntegrityCommand.

   Auth: VerifyPinCommand (bcrypt-сверка, блокировка на 30 сек после 5
   неудачных попыток), ChangePinCommand, LockSessionCommand.

   Discounts/Currency (раздел 17.7): ApplyVisitDiscountCommand (обязательная
   причина при скидке > 0, пишет в DiscountHistory — append-only),
   UpdateExchangeRateCommand.

   WaitingList (раздел 17.10): AddToWaitingListCommand,
   GetMatchingWaitingListQuery (подбор подходящих пациентов при отмене визита).

4. Реализуй BackupService (Infrastructure, вызывается из Application через
   интерфейс): pg_dump в custom-формате через портативный pg_dump.exe →
   SHA-256 хэш файла и .sha256 рядом → AES-256 шифрование бэкапа ключом,
   производным от PIN/мастер-пароля → запись в BackupRecords. Отдельно —
   RestoreService: расшифровка → сверка хэша → safety-backup текущего
   состояния → pg_restore → сигнал на перезапуск приложения.
   Ротация: daily (retention из Settings, по умолчанию 30 дней), manual
   (не удаляются), pre-update (хранить последние 5).

5. Фоновые сервисы (BackgroundService/IHostedService), заготовки для фазы 6,
   но реализовать логику уже сейчас:
   - DailyBackupBackgroundService — раз в 24 часа, и обязательно проверка
     при каждом старте "последний backup был больше 24ч назад?" (раздел
     17.13, режим для ноутбука, который выключается на ночь).
   - LowStockCheckBackgroundService — периодическая проверка материалов
     ниже MinStockThreshold.
   - AttachmentIntegrityCheckBackgroundService — периодическая фоновая
     проверка SHA-256 вложений на повреждение/отсутствие файла (раздел 11).

6. IMemoryCache для каталога процедур, справочников МКБ-10/11, Settings —
   с инвалидацией при изменении (раздел 12).

7. Предзаполнение каталога процедур (раздел 19.6) — сидинг-скрипт/команда
   SeedInitialCatalogCommand, вызывается один раз при первом старте: полный
   список позиций по 9 специальностям (раздел 19.5) с PriceMin/PriceMax
   там, где нужен диапазон (рентген, расходники, пломбирование, лечение
   кариеса по трём степеням глубины, коронки), и отдельные растущие по цене
   позиции "Отток 1/2/3/4 канал".

8. Unit-тесты (xUnit) для всех Handler'ов, валидаторов, и отдельно —
   доменной логики расчёта долга (VIEW-эквивалент в памяти), списания
   материалов, начисления гарантии (WarrantyMonths → дата окончания).
   Цель покрытия для финансовых и одонтограммных хендлеров — не менее 80%.

DEFINITION OF DONE:
- [ ] Все команды/запросы из раздела 5 + доработки раздела 17/19 реализованы
- [ ] ValidationBehavior и AuditLoggingBehavior подключены в pipeline и
      покрыты тестами (невалидная команда не доходит до хендлера; валидная
      команда с изменением данных создаёт запись в AuditLog)
- [ ] CreateVisitCommand атомарно создаёт Visit+VisitProcedure+ToothSurfaceHistory
      +обновление LastVisitDate+списание материалов в одной транзакции —
      подтверждено интеграционным тестом с намеренным сбоем на последнем шаге
      (весь визит должен откатиться)
- [ ] BackupService создаёт зашифрованный .backup + .sha256, RestoreService
      успешно восстанавливает на тестовой БД
- [ ] Каталог процедур предзаполняется по разделу 19.6 при первом запуске
- [ ] Тесты зелёные, покрытие финансовых/одонтограммных модулей ≥80%
```

## ЧАСТЬ 3 / 6 — WebApi: контроллеры, middleware, аутентификация

```
Продолжение проекта Dental IS. ФАЗА 3 из 6. Application-слой (CQRS, валидация,
аудит, backup) уже реализован в фазе 2. Твоя задача — открыть его наружу через
REST API на ASP.NET Core, добавить middleware и PIN-аутентификацию. UI (Blazor)
пока не трогаем — только API, который в следующих фазах будет вызывать клиент.

ЗАДАЧИ ЭТОЙ ФАЗЫ:

1. Настрой Program.cs полностью: регистрация MediatR, FluentValidation,
   AutoMapper, DbContext, Serilog, всех сервисов из фазы 1-2 через DI,
   CORS (разрешить только localhost, т.к. всё локально), Kestrel на порту
   из appsettings.json (по умолчанию 5000, fallback на следующий свободный
   порт, если занят — реализуй проверку занятости и авто-инкремент).
   При старте — открытие системного браузера по умолчанию на
   http://localhost:{port} (Process.Start с useShellExecute).

2. Реализуй все контроллеры из раздела 6 ТЗ, тонкие, делегирующие в MediatR,
   базовый путь /api/v1/:
   - PatientsController, VisitsController, TeethController,
     TreatmentPlansController, PaymentsController, AttachmentsController,
     MaterialsController, RemindersController, AnalyticsController,
     BackupController, AuthController, SettingsController.
   - Дополнительно (по доработкам фазы 2): DiscountsController /
     CurrencyController, WaitingListController.
   - AttachmentsController: POST multipart/form-data, GET download (стриминг
     файла с диска по относительному пути + проверка что путь не выходит за
     пределы Patients/ — защита от path traversal), DELETE (мягкое удаление).

3. Единый формат ответа для ВСЕХ эндпоинтов: { success, data, error,
   validationErrors }. Реализуй базовый ApiControllerBase с методом
   HandleResult<T>(Result<T>), который маппит Result в этот формат и
   правильный HTTP-статус (200/400/404/409).

4. GlobalExceptionHandlingMiddleware: ловит любые необработанные исключения,
   логирует полный stack trace в Serilog с уровнем Error/Fatal, клиенту
   отдаёт { success: false, error: "..." } с 500 и БЕЗ stack trace.

5. Аутентификация:
   - AuthController: POST /auth/login (принимает PIN, вызывает VerifyPinCommand,
     возвращает session-токен), POST /auth/change-pin, POST /auth/lock.
   - Session-токен — простой (JWT ок, но без внешних Identity Provider'ов,
     чисто локальная генерация и валидация). Токен живёт в памяти на клиенте,
     не в localStorage (это будет соблюдено в фазе 4 на стороне Blazor —
     здесь просто убедись, что API не полагается на cookie/localStorage).
   - AuthorizationMiddleware/[Authorize]-эквивалент на все контроллеры,
     кроме /auth/login и health checks.
   - Блокировка после 5 неудачных попыток на 30 секунд — состояние хранится
     в Settings/памяти сервера (не только на клиенте, иначе легко обойти).
   - Логирование попыток входа в AuditLog с типом SecurityEvent.

6. Health checks: GET /health — проверка доступности Postgres и общего
   состояния приложения (используется установщиком/трей-иконкой в фазе 6).

7. DTO и контракты в Shared-проекте: все Request/Response модели, используемые
   и WebApi, и Client. Никакой доменной логики в Shared — только контракты
   и enum'ы.

8. Swagger/OpenAPI (dev-режим only) для проверки API вручную в этой фазе,
   до готовности UI.

9. Integration-тесты контроллеров (WebApplicationFactory + Testcontainers
   для Postgres или in-memory альтернатива для CI) — минимум по одному
   happy-path и одному validation-error тесту на каждый контроллер.

DEFINITION OF DONE:
- [ ] Все контроллеры из раздела 6 + доработок реализованы, все возвращают
      единый формат ответа
- [ ] PIN-логин работает через Swagger: неверный PIN 5 раз подряд → блокировка
      на 30 сек, событие видно в AuditLog как SecurityEvent
```
