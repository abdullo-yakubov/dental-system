# Техническое задание: Локальная стоматологическая информационная система (Dental IS)

Единый файл ТЗ для реализации через Claude Code. Один врач = один администратор. Полностью локально, без сервера, без интернета, без облака. Все данные принадлежат пользователю.

---

## 1. Стек и архитектура

- Backend: C#, .NET 9, ASP.NET Core (Minimal API или контроллеры)
- Frontend: Blazor WebAssembly (Hosted model, в одном решении с backend)
- БД: PostgreSQL (локальный инстанс)
- ORM: Entity Framework Core (Code First, миграции)
- Валидация: FluentValidation
- Маппинг: AutoMapper
- Логирование: Serilog (файлы + консоль, ротация логов)
- Медиатор: MediatR (CQRS: Commands/Queries + Handlers)
- DI: встроенный Microsoft.Extensions.DependencyInjection
- Архитектура: Clean Architecture, слои:
  - `Domain` — сущности, enum'ы, value objects, доменные исключения. Без зависимостей.
  - `Application` — CQRS команды/запросы, интерфейсы репозиториев, DTO, валидаторы, маппинг-профили, бизнес-логика use case'ов.
  - `Infrastructure` — реализация репозиториев, EF Core DbContext, миграции, файловая система, backup-сервис, шифрование.
  - `Persistence` (может быть частью Infrastructure) — конфигурации EF Core (IEntityTypeConfiguration для каждой сущности), миграции.
  - `WebApi` — ASP.NET Core, контроллеры/эндпоинты, middleware, Program.cs, автозапуск PostgreSQL, health checks.
  - `Client` — Blazor WebAssembly, страницы, компоненты, сервисы HTTP-клиента, state management.
  - `Shared` — DTO, контракты, enum'ы, используемые и клиентом и сервером.
- Принципы: SOLID, DRY, KISS, YAGNI, Repository Pattern, Unit of Work, Result Pattern (Result<T> вместо исключений для бизнес-ошибок), Global Exception Handling Middleware.
- Никаких циклических зависимостей между слоями. Domain ничего не знает о верхних слоях.

## 2. Принцип локального запуска

- Один исполняемый файл/установщик. Пользователь запускает — открывается браузер (или WebView2/окно) с интерфейсом.
- `WebApi` при старте (`Program.cs`):
  1. Проверяет, установлен ли и запущен ли локальный PostgreSQL (через `pg_ctl`/проверку порта 5432 или кастомного).
  2. Если PostgreSQL не запущен — запускает его как процесс (portable PostgreSQL, встроенный в дистрибутив приложения, без системной установки — использовать embedded postgres, например через распакованный portable-бинарник PostgreSQL, хранящийся в `Database/pgsql/`).
  3. Проверяет существование БД `dental_system`, если нет — создаёт.
  4. Применяет `Database.Migrate()` автоматически.
  5. Проверяет наличие администратора/PIN-кода в таблице настроек, если нет — создаёт запись с PIN по умолчанию `1998`.
  6. Создаёт файловую структуру папок (см. раздел 3), если её нет.
  7. Делает стартовый backup БД.
  8. Запускает Kestrel, открывает системный браузер по умолчанию на `http://localhost:5000` (или запускает через WebView2 host, если используется desktop-обёртка).
- Порт настраивается в `appsettings.json`, по умолчанию 5000 (fallback на следующий свободный, если занят).
- При закрытии приложения (через кнопку "Выход" в UI, которая шлёт сигнал на graceful shutdown): выполняется финальный backup, останавливается PostgreSQL-процесс.

│   ├── pgsql/                    # portable PostgreSQL бинарники
│   └── data/                     # data directory PostgreSQL
├── Backups/
│   ├── daily/
│   │   └── backup_YYYY-MM-DD_HHmmss.backup
│   ├── pre-update/

│       ├── CT/

│       └── Reports/

### 4.10 Debt (Долг — вычисляемая витрина, либо материализованное представление)
Рассчитывается как `SUM(Visit.TotalCost) - SUM(Payment.Amount WHERE Type IN (Payment, DebtPayoff)) + SUM(Payment.Amount WHERE Type = Refund)` per Patient. Реализовать как SQL VIEW `patient_debts` с полями: PatientId, FullName, Phone, TotalDebt, LastDebtDate, LastVisitId.

## 5. CQRS / Application слой — команды и запросы (MediatR)

Для каждой сущности реализовать полный набор:

**Patients**: `CreatePatientCommand`, `UpdatePatientCommand`, `ArchivePatientCommand`, `GetPatientByIdQuery`, `SearchPatientsQuery` (пагинация, фильтры: имя, телефон, дата рождения, номер карты), `GetPatientTimelineQuery`.

**Visits**: `CreateVisitCommand`, `UpdateVisitCommand`, `CancelVisitCommand`, `CompleteVisitCommand`, `GetVisitByIdQuery`, `GetPatientVisitsQuery`, `GetUpcomingVisitsQuery` (для календаря).

**Teeth**: `UpdateToothStatusCommand`, `AddToothSurfaceRecordCommand`, `GetPatientOdontogramQuery`, `GetToothHistoryQuery`, `GetSurfaceHistoryQuery`.

**TreatmentPlans**: `CreateTreatmentPlanCommand`, `AddTreatmentPlanItemCommand`, `CompleteTreatmentPlanItemCommand`, `GetTreatmentPlanQuery`.

**Payments**: `RegisterPaymentCommand`, `RegisterRefundCommand`, `PayOffDebtCommand`, `GetPatientPaymentsQuery`, `GetDebtorsListQuery` (с фильтрами по сумме, дате).

**Attachments**: `UploadAttachmentCommand` (сохраняет файл на диск + запись в БД), `DeleteAttachmentCommand` (мягкое удаление), `GetPatientAttachmentsQuery`.

**Materials**: `CreateMaterialCommand`, `UpdateStockCommand`, `GetLowStockMaterialsQuery`, `GetMaterialUsageReportQuery`.

**Reminders**: `CreateReminderCommand`, `CompleteReminderCommand`, `GetActiveRemindersQuery`.

**Analytics**: `GetDashboardStatsQuery`, `GetRevenueByPeriodQuery`, `GetPopularProceduresQuery`, `GetPatientFlowStatsQuery`.

**Backup**: `CreateManualBackupCommand`, `RestoreBackupCommand`, `GetBackupsListQuery`, `ValidateBackupIntegrityCommand`.

**Auth**: `VerifyPinCommand`, `ChangePinCommand`, `LockSessionCommand`.

Каждая Command обрабатывается через `IRequestHandler`, возвращает `Result<T>` (успех/ошибка с сообщением, без выброса исключений на бизнес-уровне). Каждая команда с изменением данных — валидируется через `FluentValidation` Validator, который встраивается в MediatR pipeline (`ValidationBehavior`). Каждое изменение — логируется в `AuditLog` через `AuditLoggingBehavior` (pipeline behavior).

## 6. REST API (WebApi контроллеры)

Базовый путь `/api/v1/`. Для каждого модуля — контроллер, тонкий, делегирующий в MediatR:

- `PatientsController`: GET `/patients` (поиск+пагинация), GET `/patients/{id}`, POST `/patients`, PUT `/patients/{id}`, DELETE `/patients/{id}` (архивация), GET `/patients/{id}/timeline`.
- `VisitsController`: CRUD + GET `/visits/upcoming`.
- `TeethController`: GET `/patients/{id}/odontogram`, PUT `/patients/{id}/teeth/{number}`, POST `/patients/{id}/teeth/{number}/surfaces`, GET `/patients/{id}/teeth/{number}/history`.
- `TreatmentPlansController`: CRUD.
- `PaymentsController`: POST `/payments`, POST `/payments/refund`, GET `/patients/{id}/payments`, GET `/debtors`.
- `AttachmentsController`: POST `/patients/{id}/attachments` (multipart/form-data), GET `/attachments/{id}/download`, DELETE `/attachments/{id}`.
- `MaterialsController`: CRUD, GET `/materials/low-stock`.
- `RemindersController`: CRUD.
- `AnalyticsController`: GET `/analytics/dashboard`, GET `/analytics/revenue`, GET `/analytics/procedures`.
- `BackupController`: GET `/backups`, POST `/backups/create`, POST `/backups/restore/{id}`, GET `/backups/{id}/validate`.
- `AuthController`: POST `/auth/login` (PIN), POST `/auth/change-pin`, POST `/auth/lock`.
- `SettingsController`: GET/PUT `/settings`.

Все эндпоинты возвращают единый формат ответа: `{ success, data, error, validationErrors }`. Глобальный `ExceptionHandlingMiddleware` ловит необработанные исключения → 500 + лог в Serilog, никогда не отдаёт stack trace на клиент.

## 7. Blazor WebAssembly — экраны и компоненты

### 7.1 Страница входа (`/login`)
- Поле ввода PIN (маскированное, keypad-стиль как в мобильных приложениях, кнопки 0-9).
- Кнопка "Войти".
- При ошибке — тряска поля + сообщение "Неверный PIN".
- После 5 неудачных попыток — блокировка на 30 секунд с таймером.

### 7.2 Главная панель / Dashboard (`/`)
- Карточки сверху: Пациентов всего, Визитов сегодня, Доход за день/неделю/месяц/год, Должников, Сумма долга.
- График дохода по месяцам (линейный, Chart.js через JS interop или Blazor-компонент).
- Диаграмма популярных процедур (pie chart).
- Список "Ближайшие записи" (сегодня/завтра) с быстрым переходом в карточку пациента.
- Список "Последние пациенты".
- Виджет "Низкий остаток материалов" (если есть).

### 7.3 Список пациентов (`/patients`)
- Строка поиска (live-search с debounce 300ms) по ФИО/телефону/адресу/номеру карты.
- Таблица: Фото, ФИО, Телефон, Возраст, Последний визит, Долг (цветной бейдж если > 0), кнопки Открыть/Редактировать/Архивировать.
- Фильтры: по полу, по диапазону возраста, есть ли долг, дата регистрации.
- Кнопка "Новый пациент" → модальное окно/страница создания.
- Виртуальный скроллинг для больших списков (Virtualize компонент Blazor).

### 7.4 Карточка пациента (`/patients/{id}`)
Вкладки:
- **Обзор**: основные данные, фото, аллергии, хронические заболевания, кнопки "Редактировать", "Новый визит", "Архивировать".
- **Одонтограмма**: интерактивная схема/3D-модель зубов (см. раздел 8).
- **Визиты**: список визитов, таблица с датой, процедурами, стоимостью, статусом.
- **План лечения**: список планов, каждый — с чек-листом процедур и прогресс-баром выполнения.
- **Финансы**: история платежей, текущий долг, кнопка "Внести оплату", "Возврат".
- **Документы**: галерея вложений с фильтром по типу (Фото/Рентген/КТ/Документы), лайтбокс-просмотр изображений, скачивание.
- **Timeline**: хронологическая лента всех событий пациента (визиты, платежи, изменения зубов, документы) единым списком.

### 7.5 Календарь врача (`/calendar`)
- Месяц/неделя/день вид.
- Клик по слоту → создание визита.
- Цветовая индикация статуса визита (запланирован/завершён/отменён/неявка).
- Drag-and-drop переноса визита.

### 7.6 Должники (`/debtors`)
- Таблица из VIEW `patient_debts`: ФИО, Телефон, Сумма долга, Дата последнего визита, кнопка "Оплачено" (открывает модалку ввода суммы и способа оплаты) и "Открыть карточку".
- Сортировка по сумме долга.
- Экспорт в Excel/PDF.

### 7.7 Финансы/Аналитика (`/analytics`)
- Фильтр по периоду (день/неделя/месяц/год/произвольный диапазон).
- Графики: доход по времени, доход по процедурам, доход по врачу (в данном случае один врач, но заложить расширяемость).
- Таблица топ-процедур.
- Экспорт отчётов в PDF/Excel.
- Конструктор отчётов: выбор полей, фильтров, группировки → генерация таблицы + экспорт.

### 7.8 Склад (`/inventory`)
- Таблица материалов: название, остаток, единица, мин. порог (подсветка красным если ниже порога), цена за единицу.

### 7.9 Каталог процедур (`/procedures`)
- Таблица процедур с ценами, категориями, длительностью, цветом.

- Смена PIN-кода.

## 8. Одонтограмма / 3D-модель зубов

- Реализовать как интерактивный SVG (2D-одонтограмма, FDI-нумерация 11-48 для взрослых, 51-85 для детей) — приоритетный вариант как более простой в поддержке и надёжный локально, без внешних 3D-библиотек с проблемной производительностью в WASM.
- Каждый зуб — отдельный кликабельный `<g>`-элемент в SVG.
- Каждый зуб визуально разделён на 5 поверхностей (mesial, distal, occlusal/incisal, buccal/vestibular, lingual/palatal) — каждая поверхность кликабельна отдельно.
- Цветовая индикация статуса зуба/поверхности (здоров — белый/серый контур, кариес — коричневый, пломба — синий, коронка — жёлтый, имплант — серебристый, удалён — перечёркнут серым, пульпит/лечение каналов — красный, винир — голубой, трещина — оранжевая линия).
- Клик по поверхности → всплывающая панель с выбором диагноза/статуса из списка (см. enum в 4.6) + поле комментария + привязка к текущему/новому визиту → сохранение создаёт запись в `ToothSurfaceHistory` и обновляет `Tooth.Status`.
- Клик по зубу (не по поверхности) → показывает полную историю зуба (все записи из `ToothSurfaceHistory` по всем его поверхностям) в хронологическом порядке.
- Легенда цветов сбоку от одонтограммы.
- Переключатель "Взрослые зубы / Молочные зубы".
- Опционально (если останется время после реализации 2D) — 3D-модель через Three.js (npm-пакет, интеграция через JS interop в Blazor) с аналогичной логикой кликов по mesh-поверхностям зуба; 2D-одонтограмма остаётся основным и обязательным вариантом.

## 10. Резервное копирование

- Формат: `pg_dump` в custom-формате (`.backup`), выполняется через вызов portable `pg_dump.exe` из `Database/pgsql/bin/`.
- Автоматический backup: при старте приложения, при закрытии, раз в 24 часа (фоновый `IHostedService`/`BackgroundService` с таймером), перед восстановлением из бэкапа, перед применением новых миграций при обновлении версии приложения.
- Хранение: `Backups/daily/` — ежедневные, с ротацией (удаление старше `BackupRetentionDays`, настройка в Settings, по умолчанию 30 дней); `Backups/manual/` — созданные вручную, не удаляются автоматически; `Backups/pre-update/` — перед обновлением, хранятся последние 5.
- Целостность: после создания backup вычисляется SHA-256 хэш файла, сохраняется рядом в `.sha256`-файле и в БД (таблица `BackupRecords`: Id, FilePath, CreatedAt, SizeBytes, Sha256Hash, Type). При восстановлении — сверка хэша перед restore.
- Шифрование: backup-файл дополнительно шифруется AES-256 с ключом, производным от PIN-кода (или отдельного мастер-пароля), перед сохранением на диск.
- Восстановление: страница в Настройках со списком бэкапов, кнопка "Восстановить" → подтверждение (двойное, с предупреждением о перезаписи текущих данных) → расшифровка → проверка хэша → создание safety-backup текущего состояния → `pg_restore` → перезапуск приложения.
- Autosave: в UI все формы редактирования данных пациента — автосохранение черновика в `Cache/` каждые 10 секунд (для защиты от потери несохранённых изменений при сбое), с очисткой черновика при успешном сохранении в БД.

## 11. Безопасность

- PIN-код: хранится как bcrypt-хэш, не в открытом виде. По умолчанию `1998`.
- Сессия: JWT или простой session-токен, хранится в памяти Blazor (не в localStorage, чтобы не оставался при закрытии браузера) + refresh при активности.
- Автоблокировка: после `AutoLockMinutes` бездействия (нет действий мыши/клавиатуры) — экран блокируется, показывается страница ввода PIN поверх текущего состояния (без потери несохранённых данных благодаря autosave).
- Логи безопасности: попытки входа (успешные/неуспешные) пишутся в `AuditLog` с типом `SecurityEvent`.
- Защита от случайного удаления: везде мягкое удаление + `ConfirmDialog` с текстовым подтверждением для критичных операций (например, ввести "УДАЛИТЬ" в поле).
- Контроль целостности файлов: для вложений (Attachments) хранить SHA-256 хэш файла в БД, периодическая фоновая проверка на повреждение/отсутствие файла с уведомлением врача.

## 17. Дополнительные требования (уточнения врача)

### 17.1 Персонализация и часы врача
- Настройки хранят `DoctorFullName` (например "Курбонали"), используется во всех приветственных экранах.
- Dashboard: приветствие формируется динамически по текущему времени суток — "Доброе утро / Добрый день / Добрый вечер, доктор {DoctorFullName}".
- В шапке (topbar) на всех экранах отображаются живые часы (обновление раз в секунду) в формате `HH:mm:ss`, дата рядом.
- На карточке пациента и в календаре рядом с датой визита отображается время/обратный отсчёт до визита ("через 40 минут", "сегодня в 16:00").

### 17.2 Сохранение визита → история пациента (обязательный сквозной сценарий)
- При сохранении визита: запись сохраняется в `Visit`, процедуры — в `VisitProcedure`, изменения зубов — в `ToothSurfaceHistory` с `VisitId`, комментарий врача — в `Visit.DoctorNotes`, обновляется `Patient.LastVisitDate`.
- Событие немедленно отражается в "Истории визитов" и "Timeline" карточки пациента без перезагрузки страницы.
- Ничего из истории не удаляется, только помечается отменённым (`Status = Cancelled`) с сохранением записи.

### 17.3 3D-модель зубов
- Полноценная интерактивная 3D-визуализация (Three.js/Babylon.js через JS interop), 2D-одонтограмма остаётся как быстрый альтернативный режим.
- Вращение/зум модели, подсветка при наведении, клик по зубу → приближение + панель из 5 поверхностей, клик по поверхности → выбор диагноза/лечения → привязка к текущему визиту.
- Цвет обновляется мгновенно после сохранения. Переключатель "2D/3D" — данные и логика идентичны.
- Каждое действие обязательно попадает в `ToothSurfaceHistory` с `VisitId` и отображается в истории зуба и истории пациента.

### 17.4 Фоновый режим работы
- Приложение (WebView2/системный трей) при сворачивании продолжает работать в фоне.
- Иконка в трее: Открыть, Backup сейчас, Выход.
- В фоне: автосохранение черновиков (10 сек), ежедневный backup по расписанию, проверка напоминаний с системным toast-уведомлением, проверка низких остатков материалов.
- Полное закрытие — только явным выходом, с финальным backup.

### 17.5 Частичная оплата долга
- Модальное окно "Внести оплату": поле суммы предзаполнено полным долгом, редактируется вручную; быстрые кнопки "50%", "Полностью", "Другая сумма"; способ оплаты; комментарий.
- `Payment` с `Type = DebtPayoff`, `Amount = введённая сумма`. Долг пересчитывается как агрегат (VIEW `patient_debts`).
- Если сумма меньше остатка — пациент остаётся в списке должников с обновлённым остатком. Каждая частичная оплата — отдельная неизменяемая запись.

### 17.6 Комментарии врача к визиту/лечению
- Обязательное поле "Заметки врача" (`Visit.DoctorNotes`) в форме визита.
- Комментарий на уровне зуба/поверхности (`ToothSurfaceHistory.DoctorComment`) — для фиксации нюансов лечения конкретного зуба.
- Все комментарии видны в "Истории визитов" и "Timeline" пациента.
- Полнотекстовый поиск по заметкам (PostgreSQL `tsvector`/GIN индекс).

### 17.7 Мультивалюта и гибкая скидочная система
- `Settings.BaseCurrency` + таблица `Currency` (Code, Name, Symbol, ExchangeRateToBase, UpdatedAt), курс вводится вручную.
- Суммы хранятся в базовой валюте; исторические платежи хранят курс на момент операции (снапшот).
- Скидки: на уровне процедуры (`DefaultDiscountPercent`), на уровне визита (% или сумма + обязательная причина при скидке > 0), на уровне пациента (постоянная скидка, применяется автоматически, переопределяется вручную).
- Таблица `DiscountHistory` (append-only): PatientId, VisitId, DiscountType, Amount/Percent, Reason, AppliedAt.

### 17.8 Учёт рабочего времени врача и статистика загрузки
- Рабочий график врача (дни недели + часы) в Настройках, предупреждение (не блокировка) при записи вне графика.
- Раздел аналитики "Загрузка": тепловая карта по часам/дням, средняя длительность визита по типам процедур, % простоя, % отменённых/неявок.
- `GetDoctorWorkloadStatsQuery`, экспорт в PDF/Excel.

### 17.9 Информированное согласие пациента
- Для процедур с флагом `RequiresConsent` — генерация PDF "Информированное согласие" с данными пациента и описанием рисков, шаблон настраивается в Настройках.
- Сохраняется как `Attachment` типа `Document`, привязан к визиту; скан подписанной формы можно прикрепить обратно.

### 17.10 Лист ожидания и уведомления
- Таблица `WaitingList`: PatientId, DesiredDateFrom/To, ProcedureId, Notes, Status.
- При отмене визита — предложение подходящих пациентов из листа ожидания на освободившийся слот.
- Внутренние уведомления (toast + трей) о визитах, напоминаниях, низких остатках, новых записях из листа ожидания.

### 17.11 Печать документов
- Генерация PDF (QuestPDF): чек/квитанция, справка о посещении, план лечения для пациента, форма согласия — единый модуль с шаблонами на основе данных клиники из Settings.

### 17.12 Мультиязычность интерфейса
- RU/UZ/EN через `.resx`-локализацию Blazor, переключатель в Настройках, не влияет на хранимые данные.

### 17.13 Клинические и организационные проблемы врачей — доп. функции

Это то, с чем реально сталкиваются практикующие стоматологи и что должно быть закрыто системой, даже если явно не запрашивалось:

- **Забытый повторный визит / контроль после лечения** — уже есть `Reminder`, но нужен обязательный авто-триггер: после определённых процедур (лечение каналов, установка коронки, имплантация) система сама предлагает создать контрольный визит через N дней (настраиваемый интервал по типу процедуры в каталоге).
- **Путаница между одноимёнными пациентами** — карточка пациента должна показывать явное предупреждение при создании нового пациента с похожим ФИО/датой рождения ("Возможно, такой пациент уже есть") — защита от задвоения карт.
- **Забытая история аллергий на анестетики** — поле `Allergies` должно визуально выделяться (красный бейдж) прямо на карточке визита при создании нового визита, а не только в общих данных — чтобы врач не забыл проверить перед анестезией.
- **Учёт гарантии на работу** — многие клиники дают гарантию на пломбы/коронки (например 1 год). Нужно поле `WarrantyMonths` в `Procedure`/`VisitProcedure`, автоматический расчёт даты окончания гарантии, отображение в карточке зуба ("гарантия до 12.07.2027"), чтобы при жалобе пациента врач сразу видел, действует ли гарантия.
- **Фотопротокол "до/после"** — при вложении фото — возможность пометить фото как "До лечения" / "После лечения" и показывать их рядом (сравнение слайдером) в карточке визита — полезно и для контроля качества, и для демонстрации пациенту.
- **Совместное использование зубного ряда несколькими процедурами одновременно** — если один визит закрывает несколько зубов, нужна возможность быстро скопировать одинаковый диагноз/статус на несколько выбранных зубов одним действием (мультивыбор в 3D/2D одонтограмме), а не кликать по каждому отдельно.
- **Долгие пациенты без визитов ("отвалившиеся")** — отдельный отчёт/список "Пациенты без визита более N месяцев" — помогает врачу напомнить о профилактическом осмотре и не терять клиентскую базу.
- **Ошибочный ввод оплаты** — обязательная возможность создать `Refund` (возврат/сторно) с указанием причины, а не редактировать/удалять исходный платёж — сохраняет целостность финансовой истории для последующей сверки.
- **Учёт разных источников пациентов** — поле `Patient.Source` (реклама, рекомендация, соцсети и т.д.) для последующей аналитики "откуда приходят пациенты" — полезно для маркетинговых решений даже в маленькой клинике.
- **Быстрая печать номерка/расписки** — небольшая распечатка с датой и временем следующего визита, которую можно вручить пациенту сразу, без необходимости SMS.
- **Ночной/выходной режим авто-backup** — если ноутбук выключается на ночь, ежедневный backup должен также срабатывать при следующем запуске, если пропущен (проверка "последний backup был больше 24 часов назад" при каждом старте).
- **Учёт себестоимости и реальной прибыли** — помимо дохода (выручки), стоит считать прибыль с учётом списанных материалов (`MaterialUsage.QuantityUsed * PricePerUnit`) по визиту — даёт врачу честную картину, а не только "сколько заплатили".

## 19. Уточнения на основе референсной системы клиники (реальный рабочий процесс врача)

Ниже — функционал, зафиксированный по скриншотам реально используемой системы клиники (условное название в кадре — "Profident"/"MyClinic"), который обязателен к реализации, так как он отражает проверенный сложившийся рабочий процесс врача.

### 19.1 Электронная очередь / календарь — множественный выбор врача
- Хотя система рассчитана на одного врача-администратора, интерфейс календаря должен содержать выпадающий список выбора врача (`DoctorSelector`) вверху экрана — даже если в системе прописан один активный врач, поле оставляет архитектурную возможность добавления второго врача/ассистента в будущем без переписывания календаря.
- Недельный вид календаря — колонки по дням недели (ПН, ВТ, СР, ЧТ, ПТ, СБ) с датой числом под сокращением дня, почасовая сетка слева (09:00, 10:00 ... 17:00 и далее, шаг может быть настраиваемым, по умолчанию 1 час).
- Каждый занятый слот — карточка на календаре с явным диапазоном времени ("Занят 09:00–12:00", т.е. видно и начало и конец, а не только начало).
- **Статусная иконка прямо на карточке слота** (обязательно, это ключевое отличие от плоского списка):
  - Иконка часов (⏱, жёлтый/янтарный фон карточки) — визит запланирован, пациент ещё не пришёл/ожидание.
  - Иконка галочки (✓, зелёный контур) — визит завершён/пациент принят.
  - Значок "запрещено" (⊘) в углу карточки — слот заблокирован/недоступен для записи.
- **ФИО пациента отображается прямо на карточке слота** заглавными буквами (например "БОБОЕВА НУРАНГЕЗ"), под ним диапазон времени — это должно быть видно без клика, чтобы врач ориентировался по календарю с одного взгляда.
- Клик по карточке слота открывает карточку визита (см. 19.3) поверх календаря.

### 19.2 Список должников — доработка витрины
- Колонки строго в этом порядке: Дата рождения, Сумма долга, **давность долга в днях** (не просто дата возникновения, а именно счётчик "N дней", с цветовой индикацией: жёлтый бейдж для недавних долгов ~1–30 дней, красный для просроченных >90 дней), кнопка "Подробнее".
- Кнопка "Добавить пациента" остаётся доступной прямо с экрана должников (не только со страницы пациентов) — быстрый доступ.
- Отдельная кнопка/фильтр "Долг" в шапке списка пациентов — переключатель, показывающий только пациентов с задолженностью, без перехода на отдельную страницу (в дополнение к отдельному разделу "Должники" из основного ТЗ).

### 19.3 Карточка визита/записи — полная спецификация экрана
Обязательные элементы на одном экране карточки визита:
- Заголовок — ФИО пациента заглавными буквами.
- Номер телефона под заголовком.
- Дата визита и диапазон времени рядом (не единая метка, а именно "дата" + отдельно "время начала–время конца").
- Поле "Комментарий" — свободный текст (соответствует `Visit.DoctorNotes` из раздела 17.6).
- Список выбранных процедур (`ProcedureList`) — реализуется как чекбоксы или мультивыбор из каталога лечения (см. 19.5).
- Итоговая сумма визита, вычисляемая автоматически по выбранным процедурам.
- Явная отметка "Долг" рядом с суммой — если по визиту остался непогашенный остаток, сумма долга показывается прямо здесь красным (например "0.00 сумма" зелёным, если долга нет).
- **Два быстрых канала связи прямо в карточке пациента**: иконка обычного звонка (📞, инициирует `tel:` вызов через ОС) и иконка WhatsApp (🟢, инициирует `https://wa.me/{phone}` — открывает WhatsApp с номером пациента). Это заменяет необходимость вручную искать номер и открывать другое приложение.
- Кнопки действий внизу карточки: **"Подтвердить"** (фиолетовая/акцентная — подтверждает визит, меняет статус на "Подтверждён"/"В процессе") и **"Напомнить"** (голубая — ставит/отправляет напоминание пациенту, создаёт запись в `Reminder` с привязкой к визиту).
- Кнопки навигации/действий снизу экрана: **"Назад"** и **"Чек на оплату"** (зелёная, с иконкой документа) — генерирует и открывает/печатает PDF-чек по этому визиту (соответствует модулю печати документов из раздела 17.11, но обязательно доступна прямо с карточки визита одним кликом, а не только из общего меню отчётов).

### 19.4 Экран "Поставить диагноз" — отдельный шаг после выбора лечения
Обязательно реализовать как отдельный самостоятельный экран/шаг (не встроенное поле внутри общей формы визита), потому что в референсной системе это выделенный шаг рабочего процесса:
- Заголовок экрана: "Поставить диагноз".
- Поле "Лечение" — показывает нумерованным списком уже выбранные на предыдущем шаге процедуры (например "1. Девитализирующая паста (Девит-С)", "2. Расходники") в режиме только для чтения или с возможностью удаления из списка.
- Поле "Диагноз" — обязательное текстовое поле (звёздочка `*` в референсе означает обязательность), куда врач вписывает диагноз своими словами (может дополняться автокомплитом МКБ-10/11 из раздела 9 данного ТЗ, но ввод текстом должен быть доступен всегда, без принудительной привязки к справочнику).
- Это поле "Диагноз" сохраняется в `Visit.DoctorNotes` или в отдельное поле `Visit.Diagnosis` (рекомендуется завести отдельное поле `Diagnosis` varchar/text в `Visit`, чтобы не смешивать формальный диагноз со свободными заметками врача) и обязательно попадает в историю пациента и Timeline.
- Последовательность шагов создания визита должна быть: 1) Выбор специальности/категории лечения → 2) Выбор конкретных процедур из прайса → 3) Экран "Поставить диагноз" → 4) Подтверждение и сохранение визита с итоговой суммой.

### 19.5 Каталог лечения — структура по специальностям (обязательный справочник)
Каталог процедур (`Procedure`, раздел 4.3) должен группироваться по полю `Specialty`, со следующим фиксированным списком специальностей (используется как выпадающий список первого уровня перед выбором конкретной процедуры):
1. Терапевтическое лечение
2. Ортопедическое лечение
3. Хирургическое лечение
4. Ортодонтическое лечение
5. Детская стоматология (лечение)
6. Имплантация
7. Детская стоматология (хирургия)
8. Профессиональная гигиена
9. Анестезия

Поле `Procedure.Specialty` — enum с этими значениями (расширяемый список через справочник, а не жёстко зашитый enum в коде, чтобы врач мог добавить свою специальность позже через Настройки).

### 19.6 Детализированный прайс-лист — обязательные позиции по умолчанию
При первом запуске приложение должно предзаполнять каталог процедур (`Procedure`) следующим базовым набором позиций (референсные цены в сумах, редактируемые врачом после установки), сгруппированным по специальностям из 19.5:

**Терапевтическое лечение / диагностика:**
- Консультация терапевта
- Анализ
- Прицельный снимок (рентген) — диапазон цены (например 25 000–200 000), т.к. может отличаться по сложности снимка
- Расходники — отдельная позиция с диапазоном цены (25 000–100 000), используется как "довесок" к основной процедуре
- Артикаин (1 карпула) — анестетик, тарифицируется отдельно
- Медикаментозная закладка (Ca(OH)₂, йодоформ)
- Девитализирующая паста (Девит-С)
- Build-up восстановление зуба
- Закрытие перфорации MTA
- Извлечение штифта/инструмента
- Отток 1 канал / Отток 2 канал / Отток 3 канал / Отток 4 канал — **обязательно отдельные позиции с растущей ценой по количеству обработанных каналов** (это отражает реальную сложность эндодонтического лечения — чем больше каналов, тем дороже)
- Пломбирование зуба — диапазон цены
- Эстетическая реставрация зуба
- Лечение кариеса поверхностного (1 зуб)
- Лечение кариеса среднего (1 зуб)
- Лечение кариеса глубокого (1 зуб) — **три отдельных позиции по глубине поражения**, а не одна общая "лечение кариеса"

**Ортопедическое лечение:**
- Снятие слепка Зета плюс 1 челюсть
- Снятие слепка Зета + частично
- Фиксация
- Коронка цельнолитая
- Пластмассовая коронка (жидкий)
- Пластмассовая коронка PMMA
- Металлокерамика
- Металлокерамическая коронка
- Развёрнутая консультация (3D, снимки, Wax up)
- Снятие коронки (1 зуб)
- Циркониевая коронка на импланте
- Металлокерамика на импланте
- Циркониевая коронка без керамики
- Циркониевая коронка с керамикой
- Керамическая накладка E.MAX
- Винир керамический
- Винир полевошпатный
- Паучок
- Съёмный протез пластмассовый
- Протезы на имплантах

- Поле `Procedure.PriceMin` и `Procedure.PriceMax` (вместо единой `Price`, где применимо) — для процедур с диапазоном цены (рентген, расходники, пломбирование, лечение кариеса, коронки), т.к. итоговая цена часто зависит от сложности случая и уточняется врачом на месте при добавлении в визит. Для процедур с фиксированной ценой `PriceMin = PriceMax`.
- При добавлении такой процедуры в визит — врач вручную указывает точную сумму в пределах диапазона (или вне его, с подтверждением), это сохраняется как `VisitProcedure.Price` (снапшот).

### 19.7 3D-модель зубов — референс от врача (уже реализовано врачом отдельно)
Врач уже подготовил собственную 3D-модель зубов, которую нужно использовать как основу/референс визуального стиля при интеграции 3D-одонтограммы в систему (раздел 17.3). Технически это означает:
- При реализации 3D-режима в Blazor Client — предусмотреть возможность импорта готовой 3D-модели (формат glTF/GLB как наиболее совместимый с Three.js/Babylon.js) вместо генерации обобщённой геометрии с нуля.
- Структура модели должна поддерживать разбивку на отдельные интерактивные меши по каждому зубу (32 позиции FDI) с возможностью программно менять материал/цвет меша по `ToothStatus`, аналогично логике из раздела 17.3.
- Если готовая модель уже экспортирована (например из Blender) — файл размещается в `Client/wwwroot/models/teeth.glb` (или аналогичный путь), загружается через Three.js `GLTFLoader` при инициализации сцены одонтограммы.

### 19.8 Общий вывод по интеграции
Все элементы разделов 19.1–19.7 — это не альтернатива уже описанному функционалу в разделах 4–18, а **уточнение и конкретизация** того, как именно эти экраны должны выглядеть и вести себя, основанное на проверенном реальном рабочем процессе врача. При реализации в Claude Code эти уточнения имеют приоритет над более общими формулировками разделов 6–7, если возникает противоречие в деталях (например, точный порядок шагов создания визита — по разделу 19.4, а не по общей последовательности из раздела 7.4).

## 20. Порядок реализации для Claude Code

Реализовать в единой .NET-солюшн со следующими проектами: `DentalSystem.Domain`, `DentalSystem.Application`, `DentalSystem.Infrastructure`, `DentalSystem.WebApi`, `DentalSystem.Client` (Blazor WASM), `DentalSystem.Shared`. Начать с Domain-сущностей и EF Core конфигураций (включая сущности из раздела 17: Currency, DiscountHistory, WaitingList, обновлённые Procedure/VisitProcedure с WarrantyMonths, RequiresConsent, Specialty, PriceMin/PriceMax; и поле Visit.Diagnosis из раздела 19.4) → миграции → Application CQRS слой → WebApi контроллеры → Blazor UI по страницам из раздела 7, 17 и 19, в порядке: Auth → Dashboard (с часами и приветствием врача) → Patients → 3D/2D Odontogram (с импортом готовой GLB-модели по 19.7) → Календарь с иконками статусов и ФИО на карточках слотов (19.1) → Visits (пошаговый флоу: специальность → процедуры → диагноз → подтверждение, согласно 19.4–19.5, с комментариями врача, звонком/WhatsApp и кнопкой "Чек на оплату" по 19.3) → Payments/Debtors (с частичной оплатой и давностью долга по 19.2) → Analytics (включая загрузку врача) → Inventory → Settings/Backup → фоновый режим и трей. Каталог процедур предзаполнить базовым прайсом из раздела 19.6 при первом запуске. Каждый модуль должен быть рабочим end-to-end (БД → API → UI) перед переходом к следующему.
