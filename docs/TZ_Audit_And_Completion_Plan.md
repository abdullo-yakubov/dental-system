## 1. Архитектура и структура проекта

DentalLocal — **desktop/on-premise** система для одной стоматологической клиники: WPF-лаунчер поднимает локальный ASP.NET Core Kestrel-сервер (слушает только `127.0.0.1`) со встроенным портативным PostgreSQL, а UI — Blazor WebAssembly, открываемый в браузере по умолчанию. Это архитектурно осознанное решение "одна инсталляция — одна клиника", а не SaaS.

Clean Architecture, 8 проектов в `src/`:

| Проект | Назначение |
|---|---|
| `DentalLocal.Domain` | Сущности, enum'ы, репозиторные интерфейсы. Без внешних зависимостей. |
| `DentalLocal.Application` | CQRS/MediatR, `Features/{Area}/` (команда+валидатор+хендлер в одном файле), pipeline-behaviors (`ValidationBehavior`, `TransactionBehavior`, `LoggingBehavior`, `PerformanceBehavior`), `Result`/`Error` вместо исключений для бизнес-ошибок. |
| `DentalLocal.Infrastructure` | `Auth/HmacTokenService`, `Services/BackupService`, `Services/PdfService`, `Services/ExcelExportService`, `BackgroundServices/` (обслуживание, очередь джобов), `Security/` (машинный секрет через DPAPI). |
| `DentalLocal.Persistence` | EF Core (Npgsql, snake_case, схема `dental`), конфигурации, миграции, репозитории, `DbSeeder`. |
| `DentalLocal.Server` | Minimal API, `Endpoints/*.cs` (21 файл), `Middleware/` (`BearerAuthMiddleware`, `ExceptionHandlingMiddleware`), маршруты централизованы в `Shared.Common.ApiRoutes`. |
| `DentalLocal.Client` | Blazor WASM, MudBlazor, 12 страниц (`Pages/`), 34 компонента (`Components/`), в т.ч. 2D/3D одонтограмма. |
| `DentalLocal.Shared` | DTO-контракты, дублирующие клиентские enum'ы, константы. |
| `DentalLocal.Launcher` | WPF-трей-приложение, поднимает и супервизирует Server-процесс. |

Тесты: `tests/DentalLocal.Domain.Tests`, `DentalLocal.Application.Tests`, `DentalLocal.Integration.Tests` — суммарно **≈85 тестов** (подробности слабых мест покрытия — раздел 5.4).

Вспомогательное: `installer/` (Inno Setup + `build.ps1`), `tools/teeth-model-generator/` (офлайн-генератор 3D-моделей зубов на Node/Three.js, не входит в runtime).

Рантайм-папки (`Backups/`, `Database/pgsql/`, `Data/Secrets/`, `Logs/`, `Exports/`, `Imports/`, `Reports/`, `Settings/`, `Temp/`) подтверждают модель "всё хранится локально на диске клиники".

**Важно:** папка `docs/` (включая `docs/ADR/`), на которую ссылается `CLAUDE.md`, физически отсутствует в рабочей копии на момент аудита (файл `TZ_Dental_System.md` числится переименованным в git-индексе, но реально удалён из рабочего дерева) — то есть архитектурные решения задокументированы только inline-комментариями в коде ("см. п.N ТЗ", "промпт N аудита"), а не в отдельных ADR-файлах. Это отдельно отмечено как слабость (раздел 5.3) и восстанавливается этим самым документом.

## 2. Дизайн-система и UI

- Иконки — кастомный набор `LucideIcons.cs` (Lucide).
- **Переиспользуемые примитивы** (`Components/Shared/`): `GlassCard`, `ChartCard`, `PageHeader`, `EmptyState`, `LoadingOverlay`, `SkeletonList`, `SearchBox`, `VirtualListView`, `BeforeAfterSlider`, `TypedConfirmDialog`, `PinKeypad`, `AppErrorPage` — библиотека есть, копипасты разметки по страницам в целом избегает.
- **Карточки/дашборд**: `Home.razor` (главный дашборд) + `Analytics.razor`, поддержаны `DashboardEndpoints`/`AnalyticsEndpoints`/`DashboardQueries.cs`, визуализация через `ChartCard.razor`.

- **Локализация**: 3 языка (RU по умолчанию, EN, TG), по **203 ключа** в каждом `.resx` — полный паритет, хорошее качество i18n-дисциплины.
- **Адаптивность**: специализированной мобильной вёрстки/медиа-запросов не обнаружено; архитектурно это ожидаемо (сервер слушает только localhost, мобильный доступ не предусмотрен по замыслу).

## 3. Авторизация и безопасность

Модель: **единый PIN-код на всю клинику**, без учётных записей персонала.

- Вход: `Login.razor` → `POST /api/v1/auth/login` → `LoginCommandHandler` сверяет введённый код с единственной записью `AppSettings[AccessCodeHash]`.
- Хеширование: PBKDF2-SHA256, 100 000 итераций, соль 16 байт (`PasswordHasher.cs`), сравнение constant-time.
- Дефолтный код — `111111` (`DentalConstants.DefaultAccessCode`), минимальная длина нового кода — **4 символа** (`DentalConstants.MinAccessCodeLength`).
- Токен — самодельный HMAC-подписанный bearer (`{expiry}.{base64(HMAC-SHA256)}`), не JWT, без claims/ролей, живёт 12 часов (`HmacTokenService.cs`). Есть отдельная короткоживущая (5 мин) подписанная файловая ссылка для отдачи изображений пациентов (обход ограничения `<img src>` не может слать `Authorization`).
- Хранение токена на клиенте — **только в памяти WASM** (`AuthState.cs`), не в localStorage/cookie: перезагрузка страницы = повторный вход.
- Идентичность на клиенте — захардкожен единственный claim `ClaimTypes.Name = "doctor"` (`ApiAuthenticationStateProvider.cs`).
- Защита эндпоинтов — самописный `BearerAuthMiddleware`, а не ASP.NET Core `[Authorize]`/Identity; anon-список: `Login`, `/health/live`, `ResetWithRecoveryCode`, подписанные файловые ссылки.
- Брутфорс-защита: rate limiting на логине + `InMemoryLoginAttemptTracker` — экспоненциальный лок-аут (30с → 2м → 10м), не переживает рестарт процесса.
- Recovery: `GenerateRecoveryCodeCommand` (нужен текущий PIN) / `ResetAccessCodeWithRecoveryCommand` (**анонимный** эндпоинт).
- Аудит: `AuditLog` пишется на логин (успех/провал), смену PIN, изменение настроек и т.д. — но **без привязки к исполнителю**, т.к. сущности пользователя не существует.

### Оценка
Криптографические примитивы реализованы грамотно (PBKDF2, constant-time compare, HMAC, продуманный лок-аут). Но модель авторизации **принципиально однопользовательская** — это осознанное решение под one-clinic-desktop сценарий, зафиксированное в комментариях кода (Kestrel только на 127.0.0.1). Слабости и риски — раздел 5.1.

## 4. Автоматизации и фоновые процессы

Нет Hangfire/Quartz/cron-выражений — всё вручную через `while` + `Task.Delay` (`IHostedService`).

- **`DailyMaintenanceBackgroundService`** (проверка раз в 5 минут, состояние только в памяти процесса):
  - автобэкап при старте, если последнему больше 24ч;
  - ежедневный автобэкап (раз в 24ч);
  - проверка целостности файлов пациентов (раз в 12ч) — только логирует warning, не чинит;
  - уборка "осиротевших" временных файлов загрузки (>24ч);
  - проверка низких остатков материалов (раз в час) — **только логирует warning в серверный лог, не показывает уведомление в UI** — разрыв UX.
- **`JobQueue`/`JobRunnerBackgroundService`** — общий асинхронный раннер для тяжёлых операций вне HTTP-запроса (например, экспорт должников в Excel: `202 Accepted` с `jobId` → поллинг → `GET /reports/download/{jobId}`).
- **Напоминания (Reminders)** — создаются вручную персоналом на карточке визита, читаются пассивно (список к выполнению); **нет активного пуша/уведомления** в момент наступления даты и нет интеграции с внешними каналами.
- **Лист ожидания (WaitingList)** — ручной процесс, нет авто-подбора освободившегося слота.
- **Бэкапы** (`BackupService.cs`, наиболее зрелая часть системы):
  - и расписание, и ручной запуск через один и тот же метод `CreateBackupAsync`;
  - формат v2: `pg_dump` → AES-256-GCM, ключ через PBKDF2-SHA256 600 000 итераций; ручные бэкапы шифруются PIN-ом, авто — машинным секретом через DPAPI;
  - легаси-формат (AES-256-CBC, PBKDF2 10k, фиксированный пароль) поддержан только на чтение для обратной совместимости;
  - целостность — SHA-256 хэш рядом файлом `.sha256`;
  - восстановление — safety-бэкап перед restore, закрытие пула соединений, `DROP`/`CREATE DATABASE`, `pg_restore`, прогон миграций поверх восстановленной схемы, сброс `IMemoryCache`.
- **Отчёты** — PDF (договор, согласие, рецепт, чек) через `IPdfService`; Excel (должники, топ-процедуры, загрузка врача) через `IExcelExportService`.

## 5. Выявленные слабые места

### 5.1 Авторизация/безопасность
1. Единый общий PIN на весь персонал — невозможно понять, **кто именно** из сотрудников выполнил действие (аудит фиксирует "что", не "кто").
2. Нет ролей — рецепшн и врач имеют идентичный полный доступ (финансы, аналитика, настройки, бэкапы).
3. Дефолтный PIN `111111` — тривиален, если не сменён при установке.
4. Минимальная длина нового PIN — 4 символа, допускает очень слабые коды.
5. Секрет для HMAC токенов хранится в самой БД (`AppSettings[AuthTokenSecret]`) — компрометация БД = компрометация выпуска токенов.
6. Восстановление доступа по recovery-коду — **анонимный** эндпоинт: утечка recovery-кода (скриншот, лог) позволяет сбросить PIN без знания старого.
7. `appsettings.json` содержит плейсхолдер `Password=CHANGE_ME` для подключения к БД, и **инсталлятор (`installer/DentalLocal.iss`) никак не подставляет реальный пароль** — прямая проверкой `grep -i password` по `.iss`-файлу ничего не находит. Риск, что в проде так и останется дефолтный пароль, если процесс развёртывания это не покрывает отдельно.

### 5.2 UX/автоматизации
8. Проверка низких остатков материалов и проверка целостности файлов только логируются на сервере — персонал никогда не увидит это в интерфейсе без ручного похода в логи.
9. Напоминания не имеют активного канала уведомления (ни всплывающего в UI в момент наступления, ни внешнего SMS/email) — легко пропустить.
10. Состояние `DailyMaintenanceBackgroundService` (когда был последний бэкап/проверка) хранится только в памяти процесса — при рестарте сервера счётчики обнуляются, что может отложить реальный автобэкап дольше расчётного интервала.

### 5.3 Документация/процесс
11. Папка `docs/ADR/` отсутствует физически, хотя `CLAUDE.md` ссылается на неё как на источник решений — архитектурные обоснования разбросаны по inline-комментариям ("см. п.N ТЗ"), без единой точки входа.
12. Нет `.github/workflows` — отсутствует CI: сборка/тесты/линт не проверяются автоматически на пуш/PR.

### 5.4 Тестовое покрытие
13. Интеграционные тесты (`Integration.Tests`) вызывают `IMediator` напрямую через DI-скоуп, **минуя** `BearerAuthMiddleware`, `ExceptionHandlingMiddleware`, rate limiting и реальную маршрутизацию — эти компоненты вообще не покрыты тестами (нет ни одного теста через `WebApplicationFactory`/реальный HTTP pipeline).
14. Нет тестов на `Client/` (Blazor-компоненты, `AuthState`, `ApiAuthenticationStateProvider`) — ни одного bUnit-проекта.
15. Нет тестов на `BackupService` (шифрование/расшифровка, миграция схемы после restore) — критичный по риску компонент совсем не покрыт.
16. Нет тестов на `HmacTokenService` (валидация/истечение токена, подпись файловых ссылок).
17. Нет тестов на `DailyMaintenanceBackgroundService`.

### 5.5 Стилистическая несостыковка
18. Комментарий в `AppThemes.cs` заявляет стиль "без глассморфизма/блюра", но в библиотеке есть `GlassCard.razor` — нужно свериться, действительно ли компонент использует блюр/прозрачность, и либо переименовать/переработать, либо поправить комментарий.

## 6. Избыточное / повторяющееся

1. **13+ похожих CRUD-диалогов** без общего "DialogShell"-компонента (заголовок + форма + кнопки Сохранить/Отмена повторяются в каждом) — кандидат на выделение общего каркаса.
2. **Два параллельных enum-набора** (`Domain.Enums.*` и `Shared.Enums.*`, напр. `Gender`, `PaymentMethod`, `PaymentKind`) с ручным приведением `(Gender)(short)request.Gender` в каждом хендлере — источник рассинхронизации при добавлении новых значений в одну иерархию без второй.
3. **`BackupTrigger` определяется строковым `Contains("auto")`/`Contains("restore")` по полю `note`** (`BackupService.cs`) — хрупкий неявный контракт: ручной бэкап со словом "auto" в заметке ошибочно попадёт не в ту категорию. Следует заменить на явный enum-параметр в сигнатуре `CreateBackupAsync`.
4. **Неединообразная обработка ошибок в `ReportEndpoints.cs`**: PDF-эндпоинты дёргают `IUnitOfWork` напрямую и возвращают `Results.NotFound(new { error = ... })` вручную вместо стандартного `Result` + `ToApiResult()`, применяемого во всех остальных модулях; `/procedures/export` и `/workload/export` используют `Results.Problem(...)` вместо общего helper'а. Разнородность форматов ошибок между модулями усложняет унифицированную обработку на клиенте.
5. Легаси-формат бэкапов (AES-CBC) оставлен намеренно ради обратной совместимости — это **не** мёртвый код, оставить как есть.

## 7. Отсутствующий функционал относительно коммерческой стоматологической CRM

| Возможность | Статус в проекте |
|---|---|
| Multi-tenancy | Отсутствует — one-clinic-desktop архитектура (осознанно). |
| Роли персонала (админ/врач/ресепшн) | Отсутствуют — нет сущности User/Staff/Role. |

| Импорт данных | Не найден — папка `Imports/` в рантайме существует, но соответствующего endpoint'а/фичи нет. |
| SMS/email-уведомления | Полностью отсутствуют (нет интеграций SMTP/Twilio/аналогов). |
| Онлайн-запись пациентов | Отсутствует — нет публичного (вне PIN) канала записи. |
| Оплата через терминал/эквайринг | Отсутствует — `PaymentMethod` (Cash/Card/Transfer) чисто справочный, оплата фиксируется постфактум вручную. |
| Telemetry/централизованный мониторинг парка инсталляций | Отсутствует — только локальные файловые логи + `correlationId` в 500-х ошибках. |

## 8. План доработки (приоритизированный)

### P0 — безопасность/эксплуатация, сделать в первую очередь
- [ ] Убедиться, что процесс установки (`installer/`) принудительно требует смены пароля БД и PIN при первом запуске — не оставлять `CHANGE_ME`/`111111` в проде "по умолчанию".
- [ ] Поднять `MinAccessCodeLength` минимум до 6 и/или добавить проверку на "слабые" коды (`111111`, `123456` и т.п.) при смене PIN.
- [ ] Пересмотреть анонимность `ResetAccessCodeWithRecoveryCommand` — как минимум логировать/лимитировать эти попытки так же, как логин.
- [ ] Восстановить `docs/ADR/` — перенести обоснования решений из inline-комментариев в отдельные ADR-файлы (начиная с уже помеченных "промпт N аудита"/"п.N ТЗ" мест).

### P1 — качество/тестируемость
- [ ] Добавить интеграционные тесты через `WebApplicationFactory`, реально проходящие через `BearerAuthMiddleware`, `ExceptionHandlingMiddleware`, rate limiting.
- [ ] Покрыть тестами `BackupService` (шифрование/дешифрование, integrity-check, restore) и `HmacTokenService`.
- [ ] Настроить CI (`.github/workflows`): build + `dotnet test` на каждый PR как минимум.
- [ ] Унифицировать обработку ошибок в `ReportEndpoints.cs` под общий `Result`/`ToApiResult()`.
- [ ] Заменить строковый `Contains`-детект `BackupTrigger` на явный enum-параметр.

### P2 — UX/дизайн
- [ ] Свести UI-уведомления о низких остатках материалов / проблемах целостности файлов в интерфейс (тост/бейдж на дашборде), а не только в серверный лог.
- [ ] Выделить общий `DialogShell`-компонент и переписать существующие диалоги на его основе.
- [ ] Проверить/устранить несостыковку "без глассморфизма" vs `GlassCard.razor`.
- [ ] Решить, нужен ли активный канал уведомления по напоминаниям (хотя бы визуальный бейдж "просрочено X напоминаний" на дашборде).

### P3 — расширение функциональности (если требуется бизнесом)
- [ ] Роли персонала и персонализированный аудит — если планируется работа нескольких сотрудников с разграничением прав, потребуется ввести сущность `User`/`Staff`, привязать `AuditLog` к исполнителю, переработать модель токена (claims с ролью).
- [ ] SMS/email-уведомления пациентам по напоминаниям.
- [ ] Импорт данных (из Excel/CSV или конкурирующих систем) — сейчас нет вообще.
- [ ] Интеграция с эквайрингом, если нужен приём безналичной оплаты через терминал напрямую из системы.

## 9. Нефункциональные требования (закрепить при любых доработках)

- Сервер по умолчанию должен слушать только `127.0.0.1` — не открывать наружу без явного отдельного решения по безопасности (это меняет всю модель авторизации, см. раздел 5.1).
- Все read-запросы к EF Core — через `AsNoTracking()`.
- Новые сущности с медицинской историей — soft delete/архивирование, не hard delete.
- Новые HTTP-строки клиента — только через `IStringLocalizer<SharedResource>` и три `.resx`-файла одновременно (RU/EN/TG), без хардкода текста.
- Бизнес-ошибки — через `Result`/`Error`, не через исключения; новые эндпоинты должны использовать `ToApiResult()` вместо ручного формирования `Results.*`.
- Технический долг и архитектурные решения фиксировать в `docs/ADR/`, а не только в inline-комментариях.
